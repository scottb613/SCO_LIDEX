SCO LIDEX AI House Rules
========================

Current Repository Baseline
===========================

- Repository: https://github.com/scottb613/SCO_LIDEX
- Local working repository: `Y:\DEVCODE\VSwork\LIDEX`
- The GitHub default and public release branch is `master`.
- Normal development is performed on `work-in-progress`.
- At a completed release boundary, `master`, `work-in-progress`, and the
  release tag should identify the same reviewed commit.
- The current public baseline is v1.400. Update this statement when the next
  version is formally released.

Supported Build Tools
=====================

- SCO LIDEX is a 64-bit Windows .NET application targeting
  `net10.0-windows`.
- Restore/build from the repository root with:
  `dotnet build .\SCOLIDEX.csproj -c Release`
- When packages are already restored, the preferred verification build is:
  `dotnet build .\SCOLIDEX.csproj -c Release --no-restore`
- Verify formatting with:
  `dotnet format .\SCOLIDEX.csproj --verify-no-changes --no-restore`
- Build the approved self-contained Windows runtime with:
  `dotnet publish .\SCOLIDEX.csproj -c Release -r win-x64 --self-contained true`
- Do not mix files from an earlier publish into a new distributable. Publish
  into a clean staging directory and promote the complete verified result.
- If the required compiler/runtime is unavailable or an operator compile is
  needed, report that clearly and provide the exact command to run.

Repository Layout and File Placement
====================================

- The repository root is the only active SCO LIDEX source tree.
- Do not recreate a nested `SCO_LIDEX` repository or parallel source copy.
- `work-in-progress` is a Git branch, not a second filesystem directory.
- C# source and project files remain in the repository root.
- Permanent user documentation remains in the root and under `docsMaster` as
  currently organized. Matching documents must remain synchronized.
- Generated terrain templates belong under `generated-tiles` and
  `generated-lo_tiles`.
- Product assets belong under `content` or their existing dedicated folder.
- Route-local OSM extracts belong under
  `<Route>\osm_data\geofabrik`; their authoritative metadata belongs in
  `<Route>\osm_data\osm-cache.json`.
- The small shared Geofabrik index and cross-route cache registry belong under
  `%LocalAppData%\SCOLIDEX`. Do not move route settings or history into a
  purgeable cache group.
- Never list or delete the shared Geofabrik index or cross-route cache registry
  from the exit purge dialog. Only regional PBFs and incomplete PBF downloads
  are purgeable OSM cache data.
- Reference source trees `.openrails-src` and `.tsre5-src` are read-only.
- Approved distributables belong only under `dist`.
- Compiler/test output belongs only in ignored locations such as `bin`,
  `obj`, or `build-check`, and should be removed after the task when it is
  no longer needed.
- Do not include runtime logs, temporary files, local caches, route test data,
  source snapshots, or unrelated user files in commits or distributables.

AI House Rules
==============

- Rule 1 - Stay in your lane. An AI task rooted in this repository may inspect
  and read files in any other repository, but it must never create, edit,
  delete, rename, move, format, build into, or otherwise modify files in another
  repository. All coding and other writes must remain in the repository that
  owns the task. Cross-repository findings are read-only references and must be
  handed off to a separately authorized task rooted in the repository that owns
  the files, after that repository's `AI_HouseRules.txt` has been read. A shared
  feature or integration dependency does not grant write access across
  repository boundaries.
- Work by explicit Git version/tag boundaries.
- Preserve unrelated user changes in a dirty worktree.
- Before editing, inspect the current branch, status, remote, and relevant
  version/document files.
- Normal feature and repair work is done on `work-in-progress`.
- Do not create temporary Git branches, agent branches, or extra worktrees
  unless explicitly requested.
- Never repurpose `master` for unfinished work. It represents the reviewed
  public code state.
- Never rename `master` or `work-in-progress` without explicit approval.
- If a missing tool would materially improve the work, report it.
- Small builds and focused tests are allowed when needed. Run a full publish
  only when requested or when preparing an approved local/release package.
- A code change is not complete until affected code compiles, formatting and
  `git diff --check` pass, relevant behavior is tested, documentation is
  aligned, and only intended changes remain.
- Live route tests must be read-only unless the user explicitly authorizes
  writing route terrain, distant mountains, or map files.
- Treat external service failures independently. Scan must clearly report each
  data source as PASSED or FAILED, preserve failure information for the user,
  and allow viable fallback stages to run.
- Do not poll a source during Run when Scan has disabled it.
- Cache purge controls default to unchecked and may delete only exact,
  validated OSM files in a registered AppData cache root or route
  `osm_data` cache.
- Generated terrain_maps PNG files are route output. LIDEX must never list,
  purge, or remove them as cache data.
- Always clean temporary harnesses, staging folders, failed package output,
  obsolete logs, and compiler debris after the task.
- Do not delete source history, user assets, route data, or unrelated untracked
  files merely because they are not part of the current task.
- Do not commit, push, tag, merge, or publish a GitHub release unless the user
  explicitly requests the corresponding action.

Testing Runtime Updates
=======================

- After a verified code change, replace the local testing runtime targeted by
  the SCO LIDEX desktop shortcut so the user can immediately evaluate it.
- A testing-runtime replacement is not a formal Push Local. It updates only the
  clean published runtime and does not update documentation, version files, the
  release ZIP, Git branches, tags, or GitHub.
- Update documentation and rebuild the complete local package/ZIP only when the
  user explicitly requests Push Local or otherwise requests a formal local
  package update.

Version and Tag Rules
=====================

- Public versions and Git tags use the exact form `v<major>.<three digits>`.
  Examples: `v1.100`, `v1.200`, and `v1.201`.
- Do not shorten `v1.200` to `v1.2`, `v1.20`, or `1.200`.
- The tag, documentation title/version, executable version, ZIP filename, and
  GitHub release name must describe the same release.
- Keep version values aligned in at least:
  - `VERSION`
  - `SCOLIDEX.csproj` Version, AssemblyVersion, and FileVersion
  - `README.md` and `README.txt`
  - `CHANGELOG.txt` and `docsMaster\CHANGELOG.txt`
  - `INSTRUCTIONS.txt` and `docsMaster\INSTRUCTIONS.txt`
  - any versioned download links, release references, and runtime user-agent
    text
- Search the complete tracked code/document set for the old version before
  approving a new version.
- Release tags may be corrected and repointed when the user explicitly
  authorizes updating that existing release. Never move, replace, delete, or
  reuse a public tag silently or without that approval.
- Create the release tag only after the approved release commit is present on
  remote `master`.
- Verify that the local tag, remote tag, and remote `master` resolve to the
  intended commit before creating the GitHub release.

Documentation Rules
===================

- Use the established v1.100/v1.200 README and GitHub release presentation as
  the formatting model for later releases.
- Keep root text documents and their respective `docsMaster` copies synchronized.
- `README.md` is the primary formatted public overview.
- `README.txt` and `docsMaster\README.txt` must carry the same release facts in
  plain-text form.
- `CHANGELOG.txt` records the complete release changes; do not silently add
  current work to an older release after that release is capped.
- `INSTRUCTIONS.txt` must describe actual current application behavior,
  especially Scan, Run, data-source fallback, map-cache behavior, and output
  locations.
- The GitHub release page must use the approved release prose and formatting.
  For the established SCO LIDEX workflow, the release body should match the
  approved `README.md` content unless the user requests a separate body.
- Check document hashes or file contents after copying synchronized documents.

Distributable Rules
===================

- The uncompressed package is `dist\SCOLIDEX`.
- The release runtime is `dist\SCOLIDEX\SCOLIDEX-win-x64`.
- The compressed package is named
  `dist\SCOLIDEX-v<version>-win-x64.zip`.
- Keep exactly one release ZIP in `dist`.
- The ZIP must contain one top-level `SCOLIDEX` folder and must not contain a
  duplicated nested `SCOLIDEX\SCOLIDEX` package.
- Include the executable, complete self-contained runtime, required GDAL
  runtime/data files, icons, audio/assets, generated templates, and approved
  documents.
- Do not include `bin`, `obj`, `.vs`, `build-check`, `Saves`, Git
  metadata, logs, temporary files, map PBF caches, or route test data.
- Verify the executable FileVersion, required files, ZIP structure, ZIP size,
  and SHA-256 before declaring the package complete.
- Publish only the single approved ZIP as the GitHub release asset unless the
  user explicitly requests additional assets.

TST Deployment
==============

- The established local TST runtime is
  `dist\SCOLIDEX\SCOLIDEX-win-x64`.
- "Push to TST" or "Copy to TST" means create a clean self-contained win-x64
  publish and atomically replace that complete runtime directory.
- A TST deployment does not update the release ZIP, Git branches, commits,
  tags, GitHub release assets, release notes, or public documentation unless
  the user explicitly requests those additional actions.
- If the TST executable is running or files are locked, ask the user to close
  the application before retrying the deployment.

Push Local
==========

- Do not proceed until the user requests "Push Local" or equivalent.
- Confirm that work is on `work-in-progress` and identify the intended
  version.
- Review all changes for correctness, efficiency, clarity, and unnecessary
  files.
- Align the version throughout code and documentation.
- Update README, instructions, changelog, and their respective document copies.
- Run formatting, `git diff --check`, the Release build, and relevant focused
  tests.
- When requested, create a clean self-contained win-x64 publish and rebuild the
  complete `dist\SCOLIDEX` folder and its one ZIP.
- Verify the distributable without modifying the user's route data.
- Clean build/test staging when verification is complete.
- Report the final ZIP path and SHA-256.
- "Push Local" does not authorize a Git commit, network push, tag, or GitHub
  release unless the user also requests those actions.

Push Git
========

- Do not proceed until the user requests "Push Git" or equivalent.
- Complete every applicable Push Local requirement first.
- Confirm GitHub CLI authentication before an operation that requires it. If
  authorization is missing, request the minimum required CLI authorization.
- Review `git status` and stage only intended tracked source/document changes.
  Never sweep unrelated untracked user files into the commit.
- Commit the reviewed work intentionally on `work-in-progress`.
- Push `work-in-progress` to `origin/work-in-progress`.
- Promote the approved commit to `master`, preferably with a fast-forward
  merge so branch history remains simple and the reviewed commit is unchanged.
- Push `master` to `origin/master`, then verify GitHub `master` contains
  the new source and README before tagging.
- Create the exact approved annotated tag, for example:
  `git tag -a v1.201 -m "SCO LIDEX v1.201"`
- Push only that tag, then verify it resolves to the same commit as remote
  `master`.
- Create the GitHub release for the exact tag using the approved README/release
  body and the single verified ZIP asset.
- Do not create a release from `work-in-progress`, an agent branch, a stale
  commit, or an unpushed local-only commit.
- Do not force-push `master` or `work-in-progress`. Force-update a release tag
  only when the user explicitly authorizes replacing that existing release,
  and limit the push to that exact tag reference.
- After publishing, verify:
  - GitHub default branch is still `master`.
  - GitHub `master` shows the released code and README.
  - the release tag targets the intended master commit.
  - the release page formatting is correct.
  - exactly one intended ZIP asset is attached.
  - the uploaded asset name, size, and digest match the local ZIP.
  - `work-in-progress` is synchronized with the release commit before new
    development begins.

Release Recovery and Corrections
================================

- If a tag exists but remote `master` is stale, update and verify `master`
  before changing the release. Do not assume the tag alone published the code.
- When the user authorizes correcting an existing release, repoint only that
  exact tag after both branches contain the reviewed commit, replace the
  release asset deliberately, and verify the remote tag, release metadata,
  asset size, and digest afterward.
- If a release page is incomplete or incorrectly formatted, correct the release
  body from the approved README without changing the tag target.
- If the wrong or duplicate release asset was uploaded, remove only the
  incorrect asset and upload the one verified ZIP.
- If a new package changes after upload, rebuild, recalculate SHA-256, replace
  the incorrect asset deliberately, and verify the final remote digest.
- Never conceal a partial publication. Report exactly which branch, tag,
  release body, or asset still requires correction.
